> 状态：已定稿（设计基线）｜ 最后更新：2026-08-15 ｜ 负责人：微家事开发组
> 关联文档：`01-需求.md`（需求输入）· `03-待办.md`（排期）· `04-检视.md`（安全审计）· `05-开发指南.md`（落地）

## 1. 设计目标

- 一个后端、多个门面；客户端无关；多应用底座；合规与延迟分离；最小权限。
- 数据湖是 **app-agnostic 通用底座**：微家事只是第一个 `app`，新应用靠“声明 schema”接入，不改数据湖代码。
- **定位定性（2026-08-15 决议）**：当前架构已具备平台核心能力（app-agnostic、两级隔离、类型化模块设计定型），属「平台核心、客户端尚未长全」状态，而非「小程序专属过渡态」。后续重点为长出多端客户端并让代码追上设计。

## 2. 抽象层级与 App / Tenant 模型

```
平台核心（app 无关）   认证 / 两维隔离(app_id+tenant_id) / 通用数据+对象存储 / 配额
  └─ 应用层 app        如 微家事（slug: jiashiben）；声明自身数据模型、登录方式、配额
       └─ 租户 tenant  单值（运营方 = 我们）；仅为平台通用性预留，当前不真正多值
            ├─ 用户 user
            └─ 家庭 groups（分组/关系实体：成员 + 共享数据，非 tenant）
```

- **两级隔离**：所有表带 `app_id` + `tenant_id`（单库共用、逻辑隔离）；R2 前缀 `app_id/tenant_id/`。
- **微家事为单 tenant**（消费级、单一运营方）；`tenant_id` 仅为平台通用性预留，当前单值。家庭 = tenant 内部的**分组/关系实体**（`family_groups` + 共享链路），不是租户；同一账号体系下跨端映射到同一 tenant，数据共享。
- `apps` 表：应用注册（app_id / name / owner / 启用的登录方式 / 配额 / status）。
- `tenants` 表：`app_id` + `plan` / 配额 / `status`。
- 用户归属：`users` 绑 `app_id` + `tenant_id` + `openid`/`email` + provider。
- 家庭共享：`family_groups` + `shared`/`family_id` 字段控制可见性。

## 3. 客户端与认证矩阵

| 客户端 | 身份来源 | 令牌类型 | 必经网关 | 说明 |
|---|---|---|---|---|
| 小程序 | 微信 openid | T1 用户令牌 | 是（合规+备案） | 网关做 code2session |
| Web (SPA) | 账号/密码·OAuth | T2 用户令牌 | 可选（境内加速） | 直连或经网关 |
| App（原生） | 账号/密码·OAuth | T2 用户令牌 | 可选 | 同上 |
| MCP Server | API Key | T3 服务令牌 | 否 | 延迟不敏感，直连数据湖 |
| Skill（专家） | 复用 MCP | T3 服务令牌 | 否 | 零额外后端 |
| 管理后台 | 管理员账号 | T4 管理令牌 | 是（境内运营） | Web 客户端 |

## 4. 令牌体系

四类令牌统一为**可验证的 JWT**（无状态，数据湖直接验签，无需查库）：

- **公共 claims**：`sub`(主体ID) / `aid`(app_id) / `tid`(tenant_id) / `typ`(wx|user|service|admin) / `scp`(scope数组) / `exp` / `iss`(签发方) / `aud`(数据湖)
- **T1 WX 用户令牌**：网关 code2session 后签发；短期 + refresh。
- **T2 用户令牌**：Auth 服务为 Web/App 签发，非 WX 身份；与 T1 同级（user scope）。
- **T3 服务令牌（API Key）**：长生命周期，发给集成方（MCP/Skill）；显式 `scp` + 可选 `tenant_bound`；可轮转、可吊销。
- **T4 管理令牌**：admin 登录签发；含 `admin` scope，跨用户读写。
- **内部通道**：网关→数据湖仍用 `X-Sync-Key`（服务器间），不暴露给客户端。

> 关键变化：数据湖从「只信 X-Sync-Key」升级为「验证 `Authorization: Bearer <JWT>`（验签+exp+scope+tenant）」；`X-Sync-Key` 仅保留给网关内部调用，以兼容小程序现状。

## 5. JWT 算法选型（EdDSA/Ed25519）与密钥分发

### 5.1 选型对比

| 方案 | 类型 | 数据湖侧持有 | 多签发方 | 结论 |
|---|---|---|---|---|
| HS256 | 对称 | 私钥（能伪造令牌） | 难 | MVP 最快，信任边界差 |
| ES256 | 非对称 | 仅公钥 | 易 | 可用，密钥较大 |
| **EdDSA (Ed25519)** | 非对称 | 仅公钥 | 易 | **推荐** |

**推荐 Ed25519 理由**：数据湖只持公钥（被攻破也无法伪造令牌）；天然多签发方（网关签 T1/T4、鉴权服务签 T2、`api_keys` 签 T3，各持私钥，数据湖用 `kid` 选钥）；Cloudflare Workers/Node22 原生支持；密钥短、验签快。

> 若先用最小成本跑通 MVP，可临时 HS256（单一 `JWT_SECRET`），但中间件须算法无关，便于无损切换 EdDSA。

### 5.2 密钥角色与信任边界

```
签发方 (持私钥)                  验证方 (持公钥)
网关(T1/T4)  ──signs──►  数据湖 Worker（verify，强制 tenant/scope）
未来鉴权服务   ──signs T2
api_keys 签发 ──signs T3
```
- JWT header 带 `kid`；数据湖维护 `kid → 公钥` 映射，按 kid 选钥验证。

### 5.3 与 X-Sync-Key 的边界（不混用）

| 层级 | 令牌 | 用途 | 持有方 |
|---|---|---|---|
| 客户端↔服务端 | **JWT (Bearer)** | 小程序/Web/App/MCP 调 `/v1/...` | 各客户端 |
| 服务端↔服务端 | **X-Sync-Key** | 网关→数据湖内部反代、运维 | 仅网关与数据湖 |

二者**物理分离**：混用会扩大爆破半径。

### 5.4 密钥分发（安全要点）

**原则：私钥永不进仓库、永不打日志、仅经 secret 机制注入。**

| 组件 | 环境变量 | 注入方式 |
|---|---|---|
| 网关 | `JWT_PRIVATE_KEY` | `.env`（gitignore）/ 进程 env |
| 网关 | `JWT_PUBLIC_KEYS` | 同上（验其他签发方） |
| 数据湖 | `JWT_PUBLIC_KEYS` | `wrangler secret put` |

一次性生成：`openssl ed25519 -genkey -noout -out jwt_private.pem` + `openssl ed25519 -pubout -in jwt_private.pem -out jwt_public.pem`。
轮换：JWT 带 `kid` + `iat`；先并行生效新 `kid`，旧 `kid` 保留宽限期（如 7 天）后下线。

### 5.5 Token claims 示例

```jsonc
{ "alg": "EdDSA", "typ": "JWT", "kid": "gw01" }   // header
{
  "iss": "gateway", "sub": "oXYZ...", "aid": "jiashiben",
  "tid": "fam-123", "scope": ["user:read","user:write"],
  "aud": "cloudflarepool", "exp": 1756000000, "iat": 1755996400, "jti": "uuid"
}
```
- T1：`iss=gateway, aid=jiashiben, sub=<openid>, scope=[user:read,user:write]`
- T2：`iss=authsvc, aid=jiashiben, sub=<account_id>, scope=[user:read,user:write]`
- T3：`iss=authsvc, aid=jiashiben, sub=<service_id>, scope=[svc:read]`（可 `tenant_bound`）
- T4 管理令牌按 scope 分三层：
  - 平台超级管理员：`iss=gateway, scope=[admin:platform]`（无 `aid`，跨 app 跨 tenant）
  - 应用管理员：`iss=gateway, aid=<app_id>, scope=[admin:app]`（该 app 下所有 tenant）
  - 租户管理员：`iss=gateway, aid=<app_id>, tid=<tenant_id>, scope=[admin:tenant]`（仅该 tenant）

## 6. Scope 分级

资源族：`todo` `task` `archive` `family` `img` `user` `tenant`；动作：`read` `write` `admin`

| 级别 | 授予 | 边界 |
|---|---|---|
| 用户级 (user) | `read:*` + `write:todo,task,archive,family,img` | 限定自身 `tid` 与 `sub` |
| 服务级 (service) | 显式子集，如 `read:todo,archive` | 须 `tenant_bound` 或用户委派 |
| 管理级 (admin) | 分三层：`admin:platform`（跨 app/tenant）/ `admin:app`（限定 `aid`）/ `admin:tenant`（限定 `aid`+`tid`） | 跨用户，按 scope 限定 app/tenant |
| 内部 (internal) | 网关→湖服务间 | 仅 `X-Sync-Key` |

## 7. 端点契约

- **版本化**：URL 前缀 `/v1/`（破坏性变更 → `/v2/`）。
- **认证头**：客户端 `Authorization: Bearer <token>`；网关内部 `X-Sync-Key` + `X-User-Id` + `X-Tenant-Id`。
- **资源路由**（客户端 URL 保持 tenant 维度；`app` 由 JWT `aid` + tenant 反查得到，数据湖强制匹配）：
  - `GET/POST /v1/t/:tenant/todos`；`GET/PATCH/DELETE /v1/t/:tenant/todos/:id`
  - `tasks` / `archive` / `family` / `shared` / `img` 同构
  - `GET /v1/t/:tenant/me`；`GET /v1/t/:tenant/stats`（admin）
- **类型化应用模块**：`todos/tasks/archive/...` 不由数据湖硬编码，而由 app 在 `apps` 表声明的一组 **collection（带字段 schema）** 决定；数据湖提供类型感知的通用 CRUD + 查询。微家事注册 `todo/task/archive_item/family_group/family_member`。
- **平台/应用管理端点**（显式 app 维度）：
  - `GET/POST /v1/a/:app`（应用信息 / 注册）
  - `GET /v1/a/:app/tenants`（该 app 下租户列表，admin）
  - `GET /v1/apps`（平台级跨应用，超级 admin）
- **响应信封**：成功 `200 { data }`；错误 `4xx/5xx { error, message }`。
- **分页**：`?cursor=&limit=`（默认 20，最大 100）。
- **错误码**：401 未认证 / 403 无权限 / 404 不存在 / 422 参数错 / 429 限流。

## 8. 数据湖鉴权中间件（伪码）

```
app.use('*', guard)
guard:
  if headers['X-Sync-Key'] === INTERNAL_KEY:        # 网关内部调用
      ctx.user = { typ:'internal', uid: headers['X-User-Id'], tid: headers['X-Tenant-Id'] }
      return
  token = bearer(headers['Authorization'])
  if !token: 401
  p = verifyJWT(token)                               # 验签 + exp + iss + aud
  if !p: 401
  if !hasScope(p.scp, route.requiredScope): 403
  if p.aid !== resolveApp(params.tenant): 403        # 应用隔离（tenant 反查 app_id）
  if p.tid !== params.tenant: 403                   # 租户隔离
  ctx.user = p
```
> 替换现有纯 `X-Sync-Key` 守卫；保留 `X-Sync-Key` 作为 internal 通道以兼容小程序现状。

## 9. 网关职责

- 小程序：`code2session` → 签 T1（含 `aid`）→ 以 `X-Sync-Key` 转发到湖（internal 通道）。
- 未来：Web/App 账号登录端点 → 签 T2；`POST /api/admin/login` → 签 T4。
- **配置从单 tenant 升为 app 感知**：原 `TENANT_ID=jiashiben` → `APP_ID=jiashiben`；tenant 解析改为按请求（来自 JWT），而非静态配置。
- 持有：WX AppSecret、JWT 签名密钥（与数据湖共享，仅 env）、admin 凭据。

## 10. MCP / Skill 接入

- MCP Server：独立服务（或 Worker），持 T3 服务令牌（`tenant_bound`），调数据湖 REST，暴露工具 `list_todos` / `add_task` / `search_archive`。
- 工具↔scope 映射：读工具需 `read:*`；写工具需 `write:*`。
- Skill（WorkBuddy 专家）：配置型专家，复用 MCP 的 T3 令牌，零额外后端。
- 令牌轮转 / 吊销：`api_keys` 表管理。

## 11. 管理后台（单一平台级管理端应用 + 按 scope 分层）

- **一个管理端应用，三层 scope 视图**（非「每应用独立后台」）：
  - 平台超级管理员（`admin:platform`）：跨 app、跨 tenant——应用注册、配额、全局健康（`GET /v1/apps`）。
  - 应用管理员（`admin:app`，限定 `aid`）：该 app 下所有 tenant 的租户/用户/数据浏览（`GET /v1/a/:app/tenants`）。
  - 租户管理员（`admin:tenant`，限定 `aid`+`tid`）：仅该家庭/组织数据。
- **「每应用独立运维」靠 scope 隔离实现，不靠分代码**：一个 app 管理员登录后物理上不可见别的应用数据，体验等同独立后台，但代码仅一份。
- **类型化模块支撑动态渲染**：管理端按 app 声明的 collection schema 动态生成数据浏览/编辑界面，新 app 「声明即用」，零额外开发。
- 第一等客户端：带 T4 的 Web SPA；UI 托管网关（境内、快、合规）；不直连 D1，走平台 API。
- **留口**：第三方 app 若需品牌化后台，可自建客户端（管理端本质即客户端），平台不禁止。

## 12. 安全与合规

- 全令牌 HTTPS；JWT 短期 + 刷新；service token 可轮转。
- `X-Sync-Key` 仅服务器间，不下发客户端。
- 数据湖域未备案 → 仅服务间 / 集成 / 海外客户端；国内终端用户走网关。
- 最小权限；admin 严格隔离。

## 14. 实施排序原则（B1 先行）

- **B1（双模鉴权，Phase 1）**：数据湖加 JWT 验证中间件 + 网关具备签 JWT 能力；小程序维持现状（网关代理 + `X-Sync-Key`），纯向后兼容。
- **B2（账号体系，Phase 2）**：账号/OAuth 登录(T2)、`api_keys`(T3)、admin 登录(T4)。
- **依赖分析（为何 B1 先）**：B2 实质依赖 B1。若 B2 先上而数据湖仍只认 `X-Sync-Key`，账号签出的 JWT 数据湖不认 → 客户端只能全走网关代理（违背「平等客户端可直连 `/v1`」设计）；故 B2 成立须先有 B1 的 JWT 中间件。二者非并列二选一，而是先后。
- **B1 具体内容与影响**：
  - 数据湖 `src/index.js`：原纯 `X-Sync-Key` 守卫 → 双模（`Authorization: Bearer` 走 JWT 验签 + exp + scope + `aid`/`tid` 隔离；无 Bearer 回落 `X-Sync-Key` 内部通道）。小程序路径不变。
  - 网关 `server.js`：新增 JWT 签名工具（持 EdDSA 私钥），`/api/login` 后顺带签 T1 JWT（小程序暂不用，留给直连客户端）。
  - 新增密钥：`JWT_PRIVATE_KEY`（网关 env）、`JWT_PUBLIC_KEYS`（数据湖 `wrangler secret put`）。
  - **无 DB 表变更、无客户端改动**；生产风险低（纯 additive）。
- **B1 单独解锁**：用微信登录的 Web/App 直连数据湖（家庭 app 够用）；账号登录、MCP、admin 仍待 B2。

5. 密钥（已生成并验证 round-trip）：Ed25519 密钥对。

   - **数据湖公钥**（`wrangler secret put JWT_PUBLIC_KEYS`，非机密）：JSON `{"gw1":"<JWK.x 即 raw 32 字节公钥的 base64url>"}`，与 §5.5 / `auth.js` 期望格式一致。
   - 测试已用相同格式（`generateKeyPairSync('ed25519')` → `publicKey.export({format:'jwk'}).x`）覆盖，签名/验签对齐。

### 16.2 dualGuard 伪码（数据湖）
```
dualGuard(env, headers, params):
  token = bearer(headers['Authorization'])
  if token:
    p = verifyJwt(token, env.JWT_PUBLIC_KEYS)   # 验签+exp+iss+aud
    if !p: return 401
    if !hasScope(p.scp, route.requiredScope): return 403
    if p.aid !== resolveApp(params.tenant): return 403
    if p.tid !== params.tenant: return 403
    return { typ:'jwt', ...p }
  key = headers['X-Sync-Key']
  if key === env.INTERNAL_KEY:
    return { typ:'internal', uid: headers['X-User-Id'], tid: headers['X-Tenant-Id'] }
  return 403
```

### 16.3 回归与回滚
- **回归**：小程序经网关（X-Sync-Key）全链路跑通验证；新增 JWT 路径以 `curl` + T1 令牌单独验证（不进入小程序）。
- **回滚**：若 JWT 分支异常，仅需把 `app.use('*')` 回退为原 X-Sync-Key 守卫（一行改动），小程序立即恢复；JWT 分支为纯新增、不影响既有路径。
- **不触碰**：小程序前端代码、网关反代逻辑、D1 schema、现有 X-Sync-Key 值。

### 16.4 部署步骤清单（B1 上线）
> 纯 additive，小程序始终走 X-Sync-Key 分支；即便密钥未配，网关不签 JWT、数据湖不验 JWT，系统行为与 B1 前完全一致（安全降级）。

1. **数据湖（data.kapibala.icu）**
   1. 注入公钥：`wrangler secret put JWT_PUBLIC_KEYS`，值 = `{"gw1":"<raw 32B 公钥 base64url>"}`（见 §16.1(5)）。
   2. 部署：`wrangler deploy`（向后兼容：仅新增 Bearer 分支，X-Sync-Key 分支原样保留）。
   3. 冒烟：用任一 T1 JWT `curl -H "Authorization: Bearer <jwt>" https://data.kapibala.icu/t/weijiashi/todos` 应 200；无/错 token 回落 X-Sync-Key 路径不受影响。
2. **网关（home.inkspcl.com，境内服务器）**
   1. `.env` 增加 `JWT_PRIVATE_KEY`（单行 `\n` 转义 PEM，见 §16.1(5)）；其余变量不变。
   2. 重启网关。登录后响应将新增 `jwt` 字段（小程序忽略，无影响）。
3. **回滚**：数据湖改回 `app.use('*')` 为原 X-Sync-Key 守卫（一行）即恢复；网关删除 `JWT_PRIVATE_KEY` 即停止签 JWT。两处互不影响。
