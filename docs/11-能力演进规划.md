## 〇、首要架构目标：网关屏蔽数据湖，业务对数据湖「一次部署、无需感知」

> 本条为**规划总纲**，第一章之后所有能力项的取舍都服从它。
> 提出：joevan（2026-09-06）｜ 起因：对「新业务逻辑一律进数据湖」的边界追问。

### 0.1 目标定义

**业务（小程序 / Web SPA / Agent / MCP / 第三方）只依赖网关发布的语义化、版本化 API 契约；数据湖是网关背后的内部实现，其路由、字段、存储、部署位置可自由演进，业务代码零改动。**

理想态的一句话判据：

> 数据湖今天把 `/t/:tenant/todos` 改名、拆表、换存储、甚至整体迁移到另一个后端，
> **业务端一行代码都不用改**——因为业务从来没见过这个路径。

### 0.2 关键澄清：「落点在湖」与「暴露给业务」是两件事

此前 `10-零SSH部署纪律` §四.1 提出「新业务逻辑尽量进数据湖」，本条**不推翻**它，而是补上缺失的另一半：

| 维度 | 结论 | 理由 |
|---|---|---|
| **代码落点** | 仍在数据湖 | serverless、零 SSH、免备案、全球边缘，运维成本最低 |
| **契约归属** | 必须归网关 | 业务不应依赖内部实现的路径形状 |
| **演进自由** | 数据湖可自由重构 | 只要网关契约不变，内部怎么改都与业务无关 |
| **屏蔽的实质** | 不是网络隔离，是**契约隔离** | 网络层屏蔽早已达成，真正的债在契约层 |

一句话：**业务逻辑写在湖里，业务契约长在网关上。** 两者不矛盾，缺一不可。

### 0.3 现状：屏蔽到哪一层了（成熟度评估）

| 层级 | 目标 | 现状 | 证据 |
|---|---|---|---|
| **L0 寻址屏蔽** | 业务不知道数据湖域名 | ✅ **已达成** | 小程序 `utils/sync/config.js` 的 `API_BASE = https://home.inkspcl.com`；数据湖地址仅存于网关 `.env` 的 `DATA_LAKE_BASE`（默认 `https://data.kapibala.icu`） |
| **L1 契约屏蔽** | 业务不知道数据湖路径形状 | ❌ **未达成** | `server.js` 四条通道均为「剥前缀 → 原样透传」：`/api/data/*`(457) `/api/family*`(476) `/api/t2data/*`(497) `/api/t3data/*`、`/api/t4data/*`。业务实际在请求 `/t/{tenant}/todos`、`/t/{tenant}/c/{collection}`、`/admin/*` —— **数据湖的路由形状完整泄漏给了业务端** |
| **L2 版本与灰度** | 契约可多版本并存、按租户灰度 | ❌ 未达成 | 网关无 API 版本概念；数据湖升级只能一次性全切 |
| **L3 演进无感** | 数据湖部署/故障对业务透明 | ⚠️ 部分达成 | Workers 自身部署无停机（CF 灰度），但网关侧无重试 / 降级 / 备用后端；`DATA_LAKE_BASE` 是单值 |
| **L4 多后端路由** | 可按 app/tenant 分流到不同数据湖 | ❌ 未达成 | `DATA_LAKE_BASE` 单值，无 primary/secondary 概念 |

**结论：L0 已天然具备，L1 是核心欠账**——当前「屏蔽」只是转发，业务仍在按数据湖的形状写代码。数据湖改路由 = 业务端跟着改代码，这正是 joevan 提出的痛点。

### 0.4 实施路径（渐进，遵守「稳定优先、小步低感知」）

| 步骤 | 动作 | 关键约束 |
|---|---|---|
| **S1 契约清单化** | 从 `/api/data/*` 实际调用盘点出「业务真正在用的数据湖路径」，形成网关对外契约清单 | 只盘不改，零风险；是后续一切的前提 |
| **S2 语义路由 + 外置映射表** | 网关新增 `/api/v1/*` 语义路由；内部经**外置映射表**映射到数据湖路径 | ⚠️ **映射表必须外置**（如 `gateway/routes.json`），改映射**不重启网关**——直接回应「网关改一次要宝塔重启」的成本约束 |
| **S3 旧通道冻结** | `/api/data/*`、`/api/t2data/*` 等标记 frozen，只做兼容、不再新增能力 | 存量业务零改动，新能力一律走 `/api/v1/*` |
| **S4 版本与灰度** | `/api/v1`、`/api/v2` 并存；按 app/tenant 灰度切流 | 与 A5 staging 联动：staging 数据湖可只对灰度租户生效，业务无感 |
| **S5 多后端与降级** | `DATA_LAKE_BASE` 支持 primary/secondary + 失败重试/降级 | 为多湖、多区域、容灾留口 |

### 0.5 代价与风险（必须正视，不能只讲收益）

1. **网关从「透传者」变成「契约持有者」**，维护成本上移；多一层映射 = 多一处故障点。
2. **网关成为强单点**：境内单台 VPS（1690MB 内存）。屏蔽一切后，网关挂 = 全部业务挂；而未屏蔽时数据湖理论可用性更高。
   → **前置条件**：A2 监控告警、A4 部署后冒烟、A6 一键回滚必须先落地，再谈加厚网关职责。
3. **映射表配置化有「写错全站挂」风险** → 映射表需启动校验 + 解析失败时**回落原透传**（fail-open），绝不因配置错误放大故障。
4. **迁移纪律**：不做一次性大切换。按通道逐个迁移（新能力先行，存量后动），每个通道独立验证。

### 0.6 与既有纪律的关系

`10-零SSH部署纪律` §四.1 建议增补一句：

> 新业务逻辑尽量进数据湖 **（内部实现）**，但对外契约由网关持有并屏蔽 **（外部契约）**；
> 数据湖的任何演进都不应导致业务端改动。

### 1.3 分工边界与分流准则（服从 §〇 总纲）

1. **代码落点：新业务逻辑一律进数据湖**——本地 `wrangler deploy` 天然零 SSH、免备案、跑在全球边缘。
2. **契约归属：对外一律由网关持有并屏蔽数据湖**——数据湖演进不得传导为业务端改动（**本次新增，最高优先级**）。
3. **网关只留薄代理 + 契约映射 + admin 静态 + deploy 触发 + 令牌签发**，保持稳定少改（改一次要宝塔重启，风险与成本都高）；映射表外置以避免因改映射而重启。
4. **只有必须境内 / 依赖微信会话 / 持有密钥的能力才留网关**（如 T1 签发、X-Sync-Key 注入）。
5. **VPS 当牲口不当宠物**：漂移就重跑 `setup-server.sh` 重建，不做 SSH 手术。

## 三、建议排期（尊重「稳定优先、小步低感知」）

| 阶段 | 建议项 | 判据 |
|---|---|---|
| **近期（1–2 周）** | **G2 契约清单 · G1 语义路由+外置映射** · A1 CI · A2 监控告警 · A3 备份调度 · A4 部署后冒烟 | 契约类为「只盘不改/加映射」，保险类不改业务语义，风险最低；G 组服务首要目标 |
| **中期（1–2 月）** | A5 staging · A6 回滚 · A7 requestId · A8 安全头 · **G3 旧通道冻结 · G4 契约测试** · B1 JWT 吊销 · B2 密钥过期 · C1 R2 生命周期 · C3 批量/增量 | 需要小步改造 + 重启窗口，逐项验证 |
| **远期（季度+）** | **G5 多后端 · G6 契约版本化** · B3 T2 自助 · C2 软删除 · D1 schema 校验 · D2 配额 · D3 事件 · E1 MCP 扩展 · C7 app_id 债 | 依赖业务节奏与多 app 接入时机；C7 建议排在 G1 之后，由网关吸收破坏性 |

## 四、暂不建议（沿用既有决议）

- 管理后台 / 小程序**视觉大改**（已决议：功能未稳定前不大改 UI）。
- 数据湖**分库分表**（当前单库逻辑隔离够用，分库收益低于复杂度）。
- 引入重型框架（保持零依赖 / 薄实现，契合 Worker 与 VPS 资源约束）。
- App 原生接入（挂起中）。
- **一次性把旧通道全量切到 `/api/v1`**（违反小步低感知；按通道逐个迁移，见 G3）。
