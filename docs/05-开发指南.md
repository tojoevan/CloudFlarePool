# 05 · 开发指南（环境 / 部署 / 规范 / 发布节奏）

> 状态：评审中 ｜ 最后更新：2026-08-15 ｜ 负责人：微家事开发组
> 关联文档：`02-设计.md`（架构）· `04-检视.md`（检查清单/合规）· `06-变更日志.md`（版本基线）

## 1. 目的

面向开发与运维的落地手册：如何搭建、部署、遵循约定、按节奏发布。

## 2. 环境搭建

### 2.1 前端小程序（jiashiben）
- 微信开发者工具打开 `jiashiben/`；`project.config.json` 含真实 AppID（本地、已 gitignore，clone 后用 `project.config.example.json` 重建）。
- 云端开关：`utils/sync/config.js` 的 `CLOUD_ENABLED` 与 `API_BASE`。

### 2.2 数据湖（cloudflarepool，平台核心）
- `npm install`；本地用 Miniflare 跑 smoke：`npm run bundle:test` 打包 `src/index.js` → `dist/test-bundle.mjs`，再 `node test/smoke.test.js`。
- D1/R2 绑定通过 Miniflare 内存绑定；远端用 `wrangler` 部署。

### 2.3 网关（cloudflarepool/gateway + jiashiben/backend/relay）
- Node.js 网关：`gateway/server.js`（隐私页 / health / login / data 反代）。
- nginx relay 参考：`jiashiben/backend/relay/nginx.conf` + 隐私页 `index.html`。

## 3. 部署

- **数据湖**：`wrangler.toml` 绑定自定义域 `data.kapibala.icu`、`D1`、`R2`；`INTERNAL_KEY` / `JWT_PUBLIC_KEYS` 用 `wrangler secret put`。
- **网关**：部署到境内备案服务器 `home.inkspcl.com`（根路径放隐私页，满足备案内容要求）。
- **合规**：备案域名解析须境内；数据湖域仅服务间/集成使用。

## 4. 开发规范

### 4.1 版本号进位约定（小程序）
- 格式 `X.Y.Z`，每段**单数字**，**遇 9 进位**（如 `0.0.9 → 0.1.0`）。
- 语义：`Z`=修复/小改、`Y`=功能迭代、`X`=大版本重构。
- 上传时 MP 后台务必填清「版本号 + 更新日志」，方便回滚。

### 4.2 开源脱敏规范
- 示例/模板文件（`.env.example`、`*.example`、README 占位片段）一律不写真实域名/IP/凭据，改用占位符（如 `https://your-datalake.example.com`、`wx你的AppID`、`change-me`）。
- 真实部署值只在自己的 `.env`（gitignore 保护）/ 私有文档中，绝不进模板与仓库可公开文件。

### 4.3 密钥与配置管理
- JWT 私钥：`JWT_PRIVATE_KEY`（网关 `.env`，gitignore）；数据湖仅持 `JWT_PUBLIC_KEYS`（secret 注入）。
- 内部密钥：`X-Sync-Key` / `INTERNAL_KEY` 仅网关与数据湖持有，不下发客户端。
- 所有密钥经 env / secret 注入，不入仓库、不打日志。

## 5. 发布维护节奏（小程序）

### 5.1 先判断现在「能不能发」
- **首次备案、管局审核中 → 不能发布上线**（错误码 `86369`；期间二维码可能不可用）。须等备案号。
- **已备案过、只是更新/变更备案审核中 → 不影响发布**（可正常提审与发布）。
- 核对：MP 后台 → 设置 → 小程序备案，确认「首次」还是「更新」。

### 5.2 备案中（当前阶段）
- **开发照常、发布冻结**：本地改码 / 预览 / 传体验版自测 ✅；提交审核/全量发布 ⚠️ 首次备案期被拦截，攒批待通过后统一发。
- **备案关键动作（比开发更紧急）**：
  1. 盯死 12381 短信：收到后 **24 小时内**登录 `beian.miit.gov.cn` 核验，超时退回重来。
  2. 保持电话畅通：接 **0755 开头**微信备案回访，不接可能驳回。
  3. 管局审核 1–20 工作日（均 5–10 天）；驳回后重审约 7 工作日。
  4. 备案期间别动主体/域名/小程序名称。
- **改名风险**：若正式账号名仍带「测试」等词，趁早改（未发布免费改 2 次/年），但**建议备案通过后再处理**，勿并行。

### 5.3 备案通过后
- **攒批发布**：紧急故障立即热修；体验优化/小修攒 1–2 周或一个点打一批发，勿每个 bug 都传。
- **发布流程**：开发版/体验版自测 → 提交审核（填更新日志）→ 审核通过 → **分阶段发布**（先 5%/10% 灰度，无异常再全量）。涉及数据结构改动务必灰度 + 留回退预案。
- **频率**：日常迭代每 1–2 周提审一次。**周二上午提审最快、周五下午最慢**。
- **审核时效**：微信审核通常 1–3 小时。

### 5.4 节奏口诀
> **开发不停、发布分层；备案优先、攒批上线；整退编译、灰度回退。**

## 6. 发布流程（端到端运行手册）

> 状态：已定稿 ｜ 最后更新：2026-08-15 ｜ 负责人：微家事开发组
> 关联：`04-检视.md` §3（发布前清单）· `07-测试.md` §5.4（前端门禁）· `03-待办.md`（known-broken 登记）· `06-变更日志.md`（版本基线）
> 本文只做**编排与 Gate 判定**，详细检查项以 04/07 为准，不重复罗列。

### 6.0 原则与角色
- **核心原则**：不应发布有问题版本；任何"已发现未修复"缺陷在修复验证前冻结上传（见 `07-测试.md` §5.4③）。
- **发布分层**：前端（小程序）与后端（数据湖 / 网关）各自有门禁，互不阻塞；但**同一次功能发布需两端都过门禁**才对外生效。
- **灰度回退**：涉及数据结构 / 鉴权改动务必灰度 + 留回退预案。
- **角色**：开发 = 发布负责人（当前单人项目，同一人执行与自检，但须严格走 Gate，不得跳过）。
- **审核窗口期**：提审后至过审前，门禁收紧为「全过才许下一次上传」，详见 §6.6。

### 6.1 Gate 0 · 发布准入
- [ ] **备案状态判定**：首次备案审核中 → 冻结上传（见 §5.1/5.2）；已备案或仅更新备案 → 可发。
- [ ] **known-broken 判定**：`03-待办.md` / `07-测试.md` §6 中是否存在"已发现未修复"缺陷 → 有则先修，冻结发布。
- **不通过 → 回开发，不进入后续 Gate。**

### 6.2 前端发布流（小程序）
| 步骤 | 动作 | 通过标准 | 详细依据 |
|---|---|---|---|
| 1 编译 | 开发者工具「整退重开」后 Cmd/Ctrl+B 重新构建 | 无报错；消除 `search.wxml not found` 等缓存类错误 | `04-检视` §3 |
| 2 目检 | 真机 / 体验版走核心路径 | 编辑页（删除+保存完整不偏界）、列表页（搜索+新建居中）、详情页关键按钮可见 | `04-检视` §3、`07-测试` §5.3 |
| 3 门禁 | `node scripts/lint-wxss-conflicts.mjs --strict` | 高危 0 | `07-测试` §5.4① |
| 4 前检 | 发布前清单（隐私政策 / 用户协议 PDF 等） | 材料齐备；非框架噪音不卡 | `04-检视` §3 |
| 5 上传 | MP 后台填版本号 + 更新日志 | 版本号按 §4.1 进位；日志清晰可回滚 | §4.1、`06-变更日志` |
| 6 灰度 | 分阶段发布 5%/10% → 全量 | 无异常；涉及结构改动必灰度 | §5.3 |
| 7 观察 | 灰度期监控 | 异常即回退 | §5.3、§6.4 |

### 6.3 后端发布流（数据湖 + 网关）
**数据湖（cloudflarepool）**
1. 本地门禁：`npm run bundle:test` + `node test/smoke.test.js` → **10/10 通过**（`07-测试` §5.1）。
2. 密钥（如需）：`wrangler secret put INTERNAL_KEY` / `JWT_PUBLIC_KEYS`。
3. 部署：`wrangler deploy`（自定义域 `data.kapibala.icu`）。
4. 端到端验证：`/health`→200、Bearer JWT→200、无令牌→403（`07-测试` §6 记录模板）。
5. 兼容确认：旧 X-Sync-Key 路径零影响。

**网关（home.inkspcl.com / 宝塔）**
1. 同步 B1 代码到 `/www/wwwroot/home.inkspcl.com`（**排除 `.env`**）。
2. 注入密钥（`.env` 追加 `JWT_PRIVATE_KEY` 等，gitignore 保护）。
3. **由宝塔面板重启**（勿手动 `setsid nohup` 拉起，否则面板接管异常）。
4. 验证：`/api/health`→200；用服务器真实私钥签 JWT → 数据湖 200（`07-测试` §6）。
5. **小程序代理回归冒烟（强制）**：网关重启后首件事——用小程序走 X-Sync-Key 路径全链路（登录→同步→读取）验证零影响（见 `02-设计.md` §18.8）；未通过不得视为发布完成。

### 6.4 发布后
- [ ] 更新 `06-变更日志.md`：小程序版本链 / 后端部署版本 / 文档变更。
- [ ] 灰度观察期：监控异常，备回退预案（数据湖可回滚 Worker 版本；网关可宝塔回滚）。
- [ ] 缺陷闭环：灰度发现新问题 → 记入 `03-待办.md` + `07-测试.md` §6，触发 known-broken 冻结。

### 6.5 门禁总表（一图看懂）
| Gate | 端 | 卡点命令 / 动作 | 通过标准 | 不过则 |
|---|---|---|---|---|
| G0 准入 | 共 | 备案状态 + known-broken 核查 | 可发 + 无未修缺陷 | 回开发 |
| G1 前端编译 | 前 | 整退重开 + 编译 | 无报错 | 修码 |
| G2 前端门禁 | 前 | `lint --strict` | 高危 0 | 修样式冲突 |
| G3 后端 smoke | 后 | `node test/smoke.test.js` | 10/10 | 修逻辑 |
| G4 后端上线 | 后 | health / 端到端验证 | 200 + 兼容 | 回滚 |
| G5 灰度 | 共 | 分阶段发布 | 无异常 | 回退 |

### 6.6 审核窗口期规则（提审后、过审前）
> 触发：小程序已提交审核、处于「审核中」状态（微信通常 1–7 天，期间无法快速重传）。本规则把门禁收紧为「全过才许下一次上传」。

- **只积累、不单独传**：审核中不接受"为某个小修单独重传"——重传需等驳回或撤审，代价高。所有改动先在本地的体验版 / 开发版验证、攒批。
- **下次上传前强制三道全绿**：每次准备下一次上传前，必须重新走 **Gate0 准入 + G2 `lint --strict`（高危 0）+ 真机目检（编辑页不偏界 / 列表居中 / 按钮可见）**；任一不过 → 冻结，先修。审核等待期长，最易"顺手改了却没重跑门禁"，故每次都从零重验。
- **known-broken 更严**：审核期新发现任何缺陷，立即登记 `03-待办.md` + `07-测试.md` §6，并冻结下一次上传直至修复验证（比平时更不容侥幸）。
- **被驳回处理**：微信驳回 → 先撤审 / 等驳回回调；按反馈修码后，**全部门禁（G0–G5 相关项）重走一遍**才许重新提审；严禁"只改驳回点就重传"。
- **过审瞬间复核**：审核通过、点「发布」前，再跑一次 G0+G2+真机，确认等待期没引入新改动导致回退。
