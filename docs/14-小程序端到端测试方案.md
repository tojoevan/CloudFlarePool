# 14-小程序端到端测试方案（agent 测试用户）

> 状态：方案讨论确认于 2026-09-07，**先记文档、后续实现**（用户拍板）。
> 隔离方式暂定「独立租户 agent-test」（推荐），实现时再最终确认。

## 0. 背景与目标
当前发版验证只能做到「无 token 探活」（证明链路通、鉴权在工作），**无法证明带真实身份的业务读写成功**。每次验证都依赖用户手动点小程序或提供凭据，无法自动化。

目标：设计一个**固定的 agent 测试用户**（业务身份），让自动化脚本能端到端验证小程序全链路（登录 → CRUD → 清理），每次发版后零人工介入即可拿到业务证据。

## 1. 与「Agent 部署令牌」的区别（澄清，避免混淆）
| 维度 | Agent 部署令牌（`agt_`） | agent 测试用户（本方案） |
|---|---|---|
| 身份性质 | 运维身份（部署者） | 业务身份（T2 账号，等同真人小程序） |
| 通道 | `/api/agent/*` | `/api/data/*`（与小程序完全一致） |
| 用途 | 部署网关/数据湖代码 | 自动化端到端业务测试 |
| 生命周期 | 临时、限时、可吊销 | 长期固定、仅供测试 |
| 数据归属 | 不改业务数据 | 在隔离 tenant 下产生测试数据 |

两者语义不同，**不要合并**。本方案的「agent 用户」是 QA 用的机器人账号，不是部署钥匙。

## 2. 设计
1. **独立租户 `agent-test`**：用 X-Sync-Key 通道（`tenants.js POST /`，网关可调用，零风险）创建，与 `weijiashi` 完全隔离。
2. **测试账号** `agent@kapibala.icu` + 固定强密码，挂在该租户下（T2 账号，email/password 登录）。
3. **凭据隔离**：账号密码仅存本地 git-ignored 文件（如 `~/.workbuddy/cloudflarepool-test.json`），**绝不进 git / 记忆 / 文档明文**。
4. **冒烟脚本** `scripts/smoke-miniapp.sh`：
   - 读本地凭据 → `POST /api/login` 拿 T2 token；
   - 真实增/查/改/删一条 todo（走 `/api/data/todos`）；
   - 断言每步 HTTP 2xx 且往返数据一致；
   - 脚本末尾清理测试数据。
5. **接入发版流程**：发版成功后由 Agent 自动跑该脚本，产出端到端证据，替代「请用户手动点小程序确认」。

## 3. 落地缺口与路径
- **账号创建入口缺失**（当前现状）：`account.js` 仅有 `/account/verify`（密码校验），`admin.js` 仅见 `/me/password`（改密码），**无「创建账号」接口**。落地需二选一：
  - **方案 A（推荐）**：给 `admin.js` 加「平台管理员建账号」接口（T4 平台角色调用，向 `users` 表 INSERT email/password 账号，带 `tenant_id`）。顺手补齐文档记录的「T2 无自助 / 管理员建号」缺口，属能力补全。
  - **方案 B**：直接 D1 INSERT 一条 PBKDF2 哈希账号（用 `password.js` 的 `hashPassword` 算法），绕过接口，不够优雅但快。
- **租户创建**：X-Sync-Key 通道已具备，零风险。
- **脚本调用**：网关 `/api/login` 的 email/password 分支已在（`server.js` 约 430/463 行），无需改网关。

## 4. 排期与风险
- **排期**：独立小任务，可在任一发版间隙做；建议归入「工程成熟度 P0」（监控 / 冒烟 / 回滚）一档，与「部署后自动冒烟」配套。
- **风险与对策**：
  - 测试账号凭据泄漏 → 仅影响隔离的 `agent-test` 租户，不波及真实数据；
  - 脚本 bug 误删 → 限定只删自己创建的测试 key，且 tenant 隔离；
  - **绝不给测试账号任何跨租户 / 管理权限**。

## 5. 验收标准（实现后）
- `bash scripts/smoke-miniapp.sh` 全绿：登录成功、增/查/改/删均 2xx、数据一致、无残留；
- 该脚本接入发版后自动冒烟，每次上线无需用户手动确认业务可用性。
