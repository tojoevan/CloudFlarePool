# 01 · 需求

> 状态：评审中 ｜ 最后更新：2026-08-15 ｜ 负责人：家事本开发组
> 关联文档：`02-设计.md`（方案）· `03-待办.md`（拆分与排期）· `05-开发指南.md`（落地节奏）

## 1. 目的

定义产品与平台的需求边界：既涵盖「家事本」作为首个应用的业务需求，也涵盖「多应用平台底座」的通用平台需求，为 `02-设计.md` 提供输入。

## 2. 范围

- 业务需求：家事本小程序功能。
- 平台需求：一个后端服务多端、多应用的通用能力。
- 非功能需求：合规、延迟、安全、最小权限。

## 3. 产品愿景

「家事本」帮助家庭管理**待办、事务、档案、家庭成员**，并提供**全局搜索**。它不是孤立小程序，而是整合项目的**第一个入口**；后续 Web / App / MCP / Skill 将复用同一后端。

### 3.1 家事本功能清单（基线）

| 模块 | 能力 | 状态 |
|---|---|---|
| 待办（todo） | 日常零散任务、完成/编辑/删除 | 已发布 |

## 4. 平台级需求

| # | 需求 | 说明 |
|---|---|---|
| PR-1 | 一个后端、多个门面 | 所有客户端平等消费同一套版本化、带 scope 的 REST API |
| PR-2 | 客户端无关 | 新增 Web/App/MCP/Skill 不应改动数据模型，只需申请令牌 |
| PR-3 | 多应用底座 | 数据湖 app-agnostic；新应用靠"声明 schema"接入，不改数据湖代码 |
| PR-4 | 合规与延迟分离 | 国内终端用户流量走境内网关；服务间/海外集成走数据湖直连 |
| PR-5 | 最小权限 | 默认最小 scope；admin 严格隔离 |

## 5. 各客户端需求

| 客户端 | 身份来源 | 需求要点 |
|---|---|---|
| 小程序 | 微信 openid | 经网关合规入口；首版可继续走网关代理，不改前端 |
| Web (SPA) | 账号/密码·OAuth | 需 T2 令牌；境内访问可借网关加速 |
| App（原生） | 账号/密码·OAuth | 同 Web，T2 令牌 |
| MCP Server | API Key | 需 T3 服务令牌（可 `tenant_bound`），暴露数据湖能力为工具 |
| Skill（专家） | 复用 MCP | 零额外后端，复用 T3 |
| 管理后台 | 管理员账号 | 需 T4 管理令牌；首版建议只读概览 |

## 6. 非功能需求

- **合规**：国内终端用户必经境内备案域名；数据湖域未备案，仅服务间/集成使用。
- **延迟**：国内用户路径低延迟；海外/集成路径可放宽。
- **安全**：全链路 HTTPS；JWT 短期+刷新；service token 可轮转吊销；内部密钥不暴露客户端。
- **隔离**：多应用、多租户数据逻辑隔离。

## 7. 待澄清需求（见 `03-待办.md` Q1–Q8）

- 应用开通方式（自助 vs 管理创建）
- 租户（家庭）开通与跨端绑定
- 小程序迁移策略（代理 vs 直连）
- 管理后台首版范围（只读 vs 读写）
- scope 粒度、是否立即做真多租户、配额模型、类型化模块实现形态
