## 一、架构设计（现状）

### 1.1 三层拓扑

```
业务端                网关（境内·有状态·单点）              数据湖（Cloudflare·无状态·边缘）
─────────             ────────────────────────            ────────────────────────────
微信小程序  ──T1──▶   home.inkspcl.com                     data.kapibala.icu
  /api/data/*         VPS 47.110.153.9（宝塔，1690MB）      Workers + D1(16表) + R2
  /api/family*        node server.js :3000（www 用户）      域名不对外，仅网关可达
Web SPA     ──T2──▶   /app/   →  /api/t2data/*  ─────────▶  /t/:tenant/*
管理后台     ──T4──▶   /admin/ →  /api/t4data/*  ─────────▶  /admin/*
Agent/MCP   ──T3──▶             /api/t3data/*  ─────────▶  /t/:tenant/*（scope 强制）
                      ▲ 备案域名必须落境内：这是网关存在的第一性理由
```

- **网关是唯一签发方**：四类令牌（T1 微信 / T2 账号 Ed25519 / T3 服务 HMAC-SHA256 / T4 管理员 Ed25519）均由 `gateway/lib/jwt.js` 签出；数据湖只验签、不签发。
- **合规硬约束**：备案域名必须解析到境内服务器，**严禁整域解析到境外**；数据湖免备案但只作后端，域名不对外。
- **抽象层级**：平台核心 → app（`app_id`）→ tenant（`tenant_id`）→ user，`app_id`+`tenant_id` 两级隔离，R2 前缀 `app_id/tenant_id/`。当前实际：app=`weijiashi`、tenant=`weijiashi`（单 app 单租户）。
- **双模鉴权 `dualGuard`**：数据湖全局守卫（除 `/`、`/health`）。Bearer JWT 走验签分支；无 Bearer 回落 `X-Sync-Key` 内部通道（小程序走此路，字节级未动、向后兼容）。

### 1.2 架构总纲（2026-09-06 确立，最高优先级）

> **契约归网关、实现归数据湖**：业务只依赖网关发布的语义化、版本化 API；数据湖是内部实现，其路由/字段/存储可自由演进，业务代码零改动。

判据：数据湖把 `/t/:tenant/todos` 改名或换存储，业务端一行都不用改。**当前未达成，详见 §四.1**。

## 四、当前五个真实缺口（按架构目标排序）

### 4.1 🔴 契约层未屏蔽（L1，首要）

网关四条通道均为**原样透传**，业务端实际持有数据湖的路径形状：

- `/api/data/*` → 剥前缀直转 `/t/{tenant}/*`（`server.js:457`）
- `/api/family*` → `family/{sub}`（`:476`）
- `/api/t2data/*` → `/t/{tenant}/{rest}`（`:497`）
- `/api/t3data/*`、`/api/t4data/*` 同理

**铁证**（小程序 `utils/sync/adapters/cloudflare.js:304`）：

```js
if (key.indexOf('/t/') === 0) return API + '/api/data' + key.slice(key.indexOf('/img/'));
```

前端为了拼出图片 URL，必须**理解数据湖的 `/t/<tenant>/img/<key>` 结构**。数据湖改这个路径，前端就得改——这正是「业务感知了数据湖」。

**业务端当前依赖的端点（约 22 个，即契约盘点的现成输入）**：

| 通道 | 端点 |
|---|---|
| `/api/data/*` | `todos`/`tasks`/`archive` 的 GET·POST·PUT·DELETE、`family/shared`、`family/shared/perm`、`family/shared/done`、`img`（上传+读取）、`me/export`、`me/deletion-request`、`me/deletion-cancel`、`me/deletion-status`、`me`(DELETE) |
| `/api/family*` | `POST /family`、`GET /family/mine`、`invite`、`invite/info`、`accept`、`members`、`leave`、`transfer`、`nickname` |
| 登录 | `POST /api/login` |

### 4.2 🔴 网关是强单点，且缺少保命三件套

网关单台境内 VPS（1690MB 内存）。若按架构目标把屏蔽职责全部压到网关，网关挂 = 全部业务挂。
**前置依赖未落地**：监控告警（A2）、部署后冒烟（A4）、一键回滚固化（A6）——目前三项全无或手工。

### 4.3 ⚠️ 稳定性工具"有脚本、无自动化"

`backup.sh` / `monitor.sh` 已写好可用，但**无定时调度、无告警通道**，实际靠人记得跑。

### 4.4 ⚠️ 单环境直连生产

`wrangler.toml` 单环境、单 D1/R2，所有 `wrangler deploy` 直接改生产，无 staging 与灰度窗口。

### 4.5 ⚠️ 身份治理缺口

JWT 无吊销（泄露即失控）、T3 密钥无过期、T2 账号无自助注册/改密/重置、管理员无全生命周期管理。

| 维度 | 评分 | 说明 |

| **功能完成度** | 高（约 80%） | 鉴权、隔离、数据面、家庭、文件、管理面、一键部署、Agent 通道均已上线验证；39 例测试 |

当前是一套"功能可用、但数据湖形状泄漏到业务端、且网关单点缺保险"的系统；下一步的重心不是加功能，而是 **①把契约收回网关（G 组）②给网关装上监控/冒烟/回滚（A 组）**。
